## 第一部分：设计哲学

### 1.1 核心思想

策略回测已经证明方向判断和胜率没有问题（ETH盈利因子14.177，XAU盈利因子15.393）。真正限制利润的是执行层过早干预，而不是策略本身的问题。

因此雷达的角色是**被动跟随、守护趋势**，不是主动锁利。入场靠TV评分系统，出场的利润兑现靠TP结构，雷达的职责是防止趋势被过早打断，而不是频繁判断方向。

### 1.2 五个层级各司其职

| 层级 | 职责 |
|---|---|
| TV策略 | 总指挥，判断方向、决定入场和出场时机 |
| 硬止损 | 最后防线，确保任何情况下单笔亏损可控 |
| TP1/TP2/TP3 | 利润兑现，逐级兑现利润，TP3占70%负责大肉部分 |
| 雷达 | 骑士守卫，TP1之前不介入，TP1之后跟随趋势上移止损，不主动判断方向 |
| 重入机制 | 补救措施，仅在雷达被噪音扫出时触发一次，以更优价格重新进场 |

### 1.3 为什么TP3占比70%

TP1和TP2负责兑现小利润，TP3负责搏大趋势。如果TP3占比太低，大趋势来临时只有少量仓位能吃到利润。高占比的TP3让策略在趋势行情中有足够的仓位暴露，同时通过雷达的动态保护来控制回撤风险。

### 1.4 不再神经质的雷达

雷达不再提前介入、不再快速上移止损、不再频繁判断要不要走。价格走到TP1附近才启动，在TP1到TP2之间保持宽松跟踪，在TP2到TP3之间逐步收紧，在TP3之后转为动态追踪直到趋势终结。

## 第二部分：Webhook消息接收与鉴权

### 2.1 TV发送的两类消息

**开仓消息**（LONG或SHORT），包含字段：`secret`（鉴权）、`action`（LONG/SHORT）、`symbol`（品种代码）、`price`（开仓参考价）、`atr`（当前ATR值）、`stop_loss`（止损价）、`tp1`、`tp2`、`tp3`（三级止盈价）、`bot_id`（机器人标识）。

**反转保护消息**（CLOSE_QUICK_EXIT或CLOSE_RSI_EXIT），包含字段：`secret`、`action`、`symbol`、`price`（平仓参考价）、`reason`（触发原因）、`bot_id`。

### 2.2 鉴权

VPS收到Webhook后，首先验证`secret`字段是否等于约定值，如果不匹配则拒绝处理，不记录为有效信号，只记录一条安全日志。

### 2.3 单账户状态管理说明

本系统是单一币安账户，所有状态（持仓、雷达档位、重入次数、订单标签等）**按品种（ETH / XAU）独立维护，两个品种之间完全隔离，互不影响**。不存在按用户区分状态的需求。状态存储结构建议：

```
state[symbol] = {
    position: {...},
    tier: 0/1/2,
    radar_status: {...},
    reentry_count: 0/1,
    pending_orders: [...]
}
```

## 第三部分：开仓消息处理流程

### 3.1 第一步：清场确认

VPS收到开仓消息后，首先查询该品种当前持仓状态。如果有持仓，执行市价全平。查询该品种所有未成交挂单，全部撤销。确认持仓归零，确认挂单列表为空。清场完成后，才能进入下一步。

### 3.2 第二步：仓位计算

VPS独立计算下单数量，不依赖TV消息中的任何数量字段。

```
下单数量 = 账户权益 × 20% × 5 / 开仓价
```

同时不超过最大杠杆限制。

### 3.3 第三步：硬止损计算

```
第一步：计算TV止损距离
tv_stop_distance = abs(webhook消息.price - webhook消息.stop_loss)

第二步：叠加呼吸垫系数（统一1.15，不分档位，见3.4说明）
actual_stop_distance = tv_stop_distance × 1.15

第三步：以VPS实际成交价为锚点计算硬止损价
多单：硬止损价 = VPS实际成交价 - actual_stop_distance
空单：硬止损价 = VPS实际成交价 + actual_stop_distance
```

**数值算例**：ETH多单，TV消息`price=1900.00`，`stop_loss=1874.00`。
- `tv_stop_distance = |1900.00 - 1874.00| = 26.00`
- `actual_stop_distance = 26.00 × 1.15 = 29.90`
- 假设VPS实际成交价`1900.80`
- `硬止损价 = 1900.80 - 29.90 = 1870.90`

### 3.4 呼吸垫系数说明（统一值，不分档位）

呼吸垫系数固定为**1.15**，适用于ETH和XAU两个品种、所有强弱趋势档位，不再按档位查表。

原因：TV策略这边的止损距离本身已经按趋势强弱分档（弱1.0倍ATR、中/强1.3倍ATR），这是策略层面对行情性质的判断。VPS这层呼吸垫的本意是补偿"K线闭合发出信号"到"VPS实际完成开仓"这段执行链路的滞后与滑点，这是执行层面的固定摩擦，和趋势强弱无直接关系。如果VPS再按档位放大一次，会与TV那层判断产生不必要的叠加放大。

这个1.15是起始值，需要在第十四部分14.3节的实盘验证阶段用真实滑点数据校准。

### 3.5 第四步：挂出止盈单

```
挂出TP1限价单，数量 = 总仓位 × 10%，价格用webhook消息.tp1
挂出TP2限价单，数量 = 总仓位 × 20%，价格用webhook消息.tp2
TP3不挂限价单，剩余70%仓位完全交给雷达管理（这一条不再有例外，详见第六部分本版修正说明）
```

### 3.6 第五步：初始化雷达状态

记录开仓价、当前ATR、当前档位（0弱/1中/2强，由VPS根据`tv_stop_distance`相对`atr`字段的比例反推，或未来TV直接传`tier`字段，见3.7），启动实时价格监控。此时雷达处于"未激活"状态，只有硬止损在保护仓位。

### 3.7 建议（可选，非强制）：Webhook补充档位字段

当前TV传给VPS的开仓消息不包含档位信息，VPS需要自己反推。建议后续TV策略脚本在开仓消息里补充`tier`字段（取值0/1/2），VPS直接读取，避免两边判断不一致的风险。短期内可暂用比例反推作为过渡方案。

### 3.8 异常处理

- 如果Webhook消息中没有`stop_loss`字段，或字段值为零或负数，**禁止开仓**并记录错误日志，不使用任何默认值兜底。
- 如果计算出的`tv_stop_distance`小于该品种最小价格变动单位（tick size）的5倍，视为异常数据，拒绝开仓并记录日志。

## 第四部分：反转保护消息处理流程

收到`CLOSE_QUICK_EXIT`或`CLOSE_RSI_EXIT`消息时，VPS执行：

1. 立即市价平掉该品种全部剩余仓位。
2. 撤销该品种所有未成交挂单（TP1/TP2/TP3限价单、硬止损单、雷达止损单）。
3. 重置该品种所有雷达状态和重入状态。
4. 记录日志，包含平仓原因。

## 第五部分：雷达止损引擎工作逻辑

### 5.1 启动机制（本版再次修正：激活门槛大幅后移，雷达使命收窄为只守护TP1-TP2中点之后的行情）

**设计原则调整**：TP1（10%仓位）和TP2前半段的利润兑现，交给已经反复验证过的永久硬止损、以及TP1/TP2各自独立的限价单去守护，雷达完全不插手这一段。雷达的使命收窄为专注保护"更晚期、更大级别"的利润（从TP1-TP2区间中点开始，一路到TP3及以后）。

**为什么这么改**：
1. TP1只占10%仓位，雷达在这一段过度敏感所冒的"提前误伤剩余70%大仓位"的风险，远大于它所能保护的这10%收益。
2. 强趋势行情经常一根K线直接推穿TP1、TP2，不给"温和回调"的机会——雷达如果在这一段就介入判断，反而容易被单边行情里的正常波动误伤出局。而重入机制本来就只留给强趋势（见第八/九部分），强趋势往往一去不回头，被误伤出局后很难拿到比原信号更优的价格重新进场，反而错过了真正的大行情——**这也是本版把重入限定在"只有强趋势才能重入"之后，反而更需要让雷达在早期少插手的直接原因**。
3. TP1、TP2的限价单本身独立于雷达运作，价格到了照样正常成交，不受雷达是否激活影响，这一段的利润兑现并不会因为雷达不插手而受损。

**新公式（改用绝对价格锚定，不再需要"距离×系数+成交价"这套计算，因为TP1/TP2本身就是固定的绝对价格）**：

```
第一步：直接取TP1、TP2的绝对价格（来自webhook消息的tp1、tp2字段，原始信号价格，不随开仓/重入变化）

第二步：根据开仓类型确定激活价格
首次开仓：
    多单：雷达激活价格 = (TP1价格 + TP2价格) / 2
    空单：雷达激活价格 = (TP1价格 + TP2价格) / 2
重入开仓：
    多单：雷达激活价格 = TP2价格
    空单：雷达激活价格 = TP2价格

第三步：激活条件（每次价格更新都要检查）
多单：当前价格 >= 雷达激活价格 时，雷达介入
空单：当前价格 <= 雷达激活价格 时，雷达介入
```

**数值算例（首次开仓）**：ETH多单，`tp1=1925.65`，`tp2=1955.00`。
- `雷达激活价格 = (1925.65 + 1955.00) / 2 = 1940.325`

**数值算例（重入开仓，同一笔信号）**：
- `雷达激活价格 = tp2 = 1955.00`，价格必须真正到达TP2，雷达才会介入。

在价格到达启动条件之前，雷达完全不介入，只有硬止损在保护仓位，TP1、TP2各自的限价单照常独立运作。价格到达启动条件时，雷达接管仓位，并将止损从硬止损位置上移至（该笔仓位实际入场价，首次开仓用首次成交价，重入用重入成交价）加减0.5倍ATR，之后按第5.2节的跟踪参数继续推进。

### 5.2 跟踪机制

雷达激活后，价格每涨一段，止损就跟进一段。跟踪步长和每次跟进幅度由当前档位决定：

**ETHUSDT.P**

| 档位 | 跟踪步长 | 每次跟进幅度 |
|---|---|---|
| 弱趋势 | 0.4倍ATR | 0.25倍ATR |
| 中趋势 | 0.5倍ATR | 0.35倍ATR |
| 强趋势 | 0.6倍ATR | 0.4倍ATR |

**XAUUSDT.P**

| 档位 | 跟踪步长 | 每次跟进幅度 |
|---|---|---|
| 弱趋势 | 0.35倍ATR | 0.2倍ATR |
| 中趋势 | 0.4倍ATR | 0.3倍ATR |
| 强趋势 | 0.5倍ATR | 0.35倍ATR |

雷达不主动判断方向，不决定何时离场，只在价格创出新高时抬高止损。

### 5.3 呼吸空间动态调节

**ETHUSDT.P**

| 区间 | 弱趋势 | 中趋势 | 强趋势 |
|---|---|---|---|
| TP1到TP2 | 0.8倍ATR | 1.2倍ATR | 1.5倍ATR |
| TP2到TP3 | 1.0倍ATR | 1.6倍ATR | 2.0倍ATR |
| TP3之后 | 1.2~1.5倍ATR | 2.0~2.5倍ATR | 2.5~3.5倍ATR |

**XAUUSDT.P**

| 区间 | 弱趋势 | 中趋势 | 强趋势 |
|---|---|---|---|
| TP1到TP2 | 0.7倍ATR | 1.0倍ATR | 1.3倍ATR |
| TP2到TP3 | 0.9倍ATR | 1.4倍ATR | 1.8倍ATR |
| TP3之后 | 1.0~1.3倍ATR | 1.8~2.2倍ATR | 2.2~3.0倍ATR |

在TP1到TP2之间保持宽松跟踪，TP2到TP3之间逐步收紧，TP3之后转为动态追踪。

### 5.4 雷达与硬止损的关系

两笔止损单同时存在，各自独立运作。价格触发雷达止损时，仓位归零后硬止损自动撤销。价格直接击穿硬止损时，仓位归零后雷达止损自动撤销。两层保护互不干扰，谁先触发谁执行。

## 第六部分：TP与雷达的共存关系（本版第三次修正：VPS不再独立拉取ATR，全程统一使用TV的atr字段）

**修正说明（第三轮，也是最终结论）**：前两轮的方案都还留了一条"VPS自己独立拉取真实ATR"的路径，或作为主选、或作为高优先级来源。**这条路径本身走不通——币安没有90分钟这个原生K线周期（ETH策略用的正是90分钟），VPS想要一个和TV口径一致的ATR，只能靠拼接更小周期的K线去合成，拼接边界一旦和TV的90分钟不完全对齐，算出来的数字照样会偏差，等于把问题往后挪了一步，没有真正解决。**

**本版最终规则：VPS完全不再尝试独立拉取或计算真实ATR，删除这整套机制。所有需要用到ATR的地方（雷达跟踪步长、每次跟进幅度、TP2-TP3呼吸空间、TP3之后呼吸空间），统一直接使用webhook消息里的`atr`字段（TV传来的值）。这是唯一的数据来源，不再区分"主/备"、不再有场景切换。**

这么做的理由很直接：TV这套评分系统的方向判断质量本身已经被反复验证过，ATR也是这套体系里一直在用、被信任的数字，没有必要再让VPS另起一条自己都拿不准的数据链路去替代它。**只用一个数据源，意味着"两边数据对不上"这类问题从设计上就不会再出现，不是把它修好，是让它没有再发生的空间。**

**TP3的最终规则（不变，再次确认）：永远不挂限价单，永远完全交给雷达管理，没有价格天花板，让它跟着趋势走到力竭为止。这条规则不再和任何ATR拉取是否成功挂钩，因为VPS已经不再尝试独立拉取ATR。**

### 6.1 各层级分工

TP1占10%、TP2占20%，均由VPS挂出限价单，价格到达即兑现。TP3占70%，**永远不挂限价单**，完全交给雷达管理这部分仓位的退出，雷达是这70%仓位唯一的主动退出路径（硬止损作为最后防线始终并存）。雷达的跟踪参数计算（第五部分的分档参数表，跟踪步长、每次跟进幅度、呼吸空间）全部使用webhook消息的`atr`字段。

### 6.2 部分成交处理与动态头寸核算（本版大幅扩写）

**背景**：实盘中TP1、TP2这两笔限价单，**不一定是一口气整笔成交的**——交易所撮合引擎可能把一笔挂单拆成多次部分成交（比如TP1这10%仓位，可能先成交3%，隔几秒再成交剩下的7%），也可能因为深度不足导致某一档长时间只成交一部分。这意味着**总持仓头寸会随着实盘推进持续、细微地变化**，不是只在"TP1整笔成交"、"TP2整笔成交"这两个离散时刻才发生变化。

**核心规则：任何一笔挂单（TP1/TP2/硬止损/雷达止损，无论哪一笔）只要发生任何数量变化的成交回报，都必须立即触发一次头寸重新核算，不能只在"整笔成交"这种大事件时才更新。**

**重新核算流程**：

1. 收到WebSocket订单成交回报（包含部分成交回报）后，从回报中读取本次成交数量，更新本地记录的"当前总持仓头寸"（当前总持仓 = 上一次记录的头寸 - 本次成交数量，平仓场景为减法，注意这里说的是多头/空头仓位本身在减少，不是新增）。
2. 立即重新计算硬止损单、雷达止损单（如果雷达已激活）**当前应有的挂单数量** = 更新后的总持仓头寸。
3. 如果重新计算出的数量和当前挂在交易所的止损单数量不一致，**立即发起改单（或撤旧单+挂新单）操作**，把止损单数量同步成最新的总持仓头寸。这个操作必须是原子的：先记录"待同步"状态到本地状态表，执行改单，改单成功后再更新状态表为"已同步"，如果改单失败要重试，不能让止损单数量长期落后于真实头寸。
4. 雷达止损价格本身的计算（跟踪步长、呼吸空间，见第五部分）**不受头寸数量变化影响**，只有挂单的"数量"字段需要跟着同步，价格该怎么算还怎么算。

**为什么这一步很重要**：如果止损单数量没有跟着实际头寸缩小而同步缩小，会出现"止损单数量比实际持仓还大"的情况——一旦触发，卖出/买入的数量超过了实际持仓，会导致**平仓变成反向开仓**（比如实际只剩70%头寸，止损单却还挂着100%的数量，触发后多卖出的30%会直接开出一笔反向空单），这是必须杜绝的严重bug，处理方式见第九部分9.4。

### 6.4 平仓操作前必须核实交易所真实持仓（本版新增）

任何触发平仓的场景（TP1/TP2/TP3成交、硬止损触发、雷达止损触发、TV反转信号），**在执行平仓下单之前，必须先用REST API查询交易所当前该品种的真实持仓数量作为最终依据，不能仅凭本地状态表的记录直接计算平仓数量**。本地记录可能因为WebSocket消息延迟、丢失、或者上一步头寸核算还没来得及同步等原因，和交易所真实状态存在微小滞后。

平仓下单的数量，**必须以这次查询到的真实持仓数量为准，且设置硬上限——平仓数量绝对不能超过查询到的真实持仓数量**，即使本地记录显示的数量更大，也以查询结果为准，宁可少平（后续可以再补一次），不能多平变成反向开仓。

## 第七部分：VPS重启状态恢复（新增章节）

### 7.1 设计原则

VPS可能因为服务器维护、程序崩溃、网络中断等原因意外重启。**重启后，正在运行中的仓位绝不能失去保护**——如果重启导致雷达状态归零、只剩硬止损裸奔，会让本该被雷达保护的浮盈完全暴露在风险中，这是不可接受的。

**核心原则：所有影响仓位安全的状态，必须持久化存储，不能只存在于内存里。**

### 7.2 需要持久化的状态清单

对每个品种（ETH、XAU），以下状态必须写入本地数据库或文件（不是仅存内存变量），且每次状态变更后立即落盘：

- 当前持仓方向、数量、开仓均价、开仓时间
- 当前档位（弱/中/强）
- 硬止损价格、硬止损订单ID
- 雷达是否已激活、雷达当前止损价格、雷达订单ID
- TP1/TP2限价单的订单ID、剩余数量、是否已成交（TP3无限价单，不适用）
- 当前重入次数（0或1）、本轮信号是否已重入过
- 本地订单状态表（第九部分）的完整快照

### 7.3 重启恢复流程

1. VPS服务启动时，**先不做任何交易操作**，读取本地持久化状态。
2. 如果本地状态显示某品种有持仓，立即查询交易所该品种的真实持仓和真实挂单列表，与本地状态交叉核对。
3. **如果本地状态和交易所真实状态一致**：恢复内存中的雷达/重入状态，继续正常监控。
4. **如果本地状态和交易所真实状态不一致**（比如本地记录有持仓，但交易所查询显示已经被平仓；或者本地记录的止损订单在交易所查不到）：
   - 以交易所真实状态为准，修正本地记录。
   - 如果发现有持仓但缺少止损保护（比如止损订单在停机期间意外被撤销或成交），**立即按照当前记录的档位重新计算并挂出硬止损单，这是最高优先级动作，必须在其他任何操作之前完成**。
   - 记录一条恢复异常日志，包含具体的不一致内容，供事后排查。
5. 恢复流程全部完成、确认持仓状态和止损保护都已就位后，才恢复正常的价格监控和信号接收。
6. 如果无法在合理时间内（建议30秒）完成恢复流程并确认止损到位，触发严重告警，人工介入，此期间该品种暂停处理新的TV信号（但已有的止损单不受影响，会正常触发）。

### 7.4 恢复期间的Webhook处理

VPS重启后的恢复流程执行期间，如果收到新的TV信号，**先缓存该信号，不立即处理**，等恢复流程完成、确认现有仓位状态安全后，再按正常流程处理缓存的信号（如果信号已经过期太久，比如超过5分钟，可以选择丢弃并记录日志，避免用过期信号做出不合时宜的操作）。

## 第八部分：重入机制

### 8.1 触发条件（必须同时满足，本版新增第5、6条）

1. 平仓来源是雷达扫出，**硬止损扫出绝对不触发重入**。
2. 平仓价格落在允许区间内：ETH多单为开仓价到开仓价+0.5倍ATR，XAU多单为开仓价到开仓价+0.3倍ATR，空单对称。
3. TV信号仍然有效，未收到反向信号或平仓信号。
4. 该方向信号下累计重入次数为零（最多一次）。
5. **【本版新增】TP1限价单尚未成交。** 如果价格曾经到达过TP1、这笔仓位10%的TP1限价单已经成交过，即使后续雷达止损被触发、且触发价格恰好也落在条件2的允许区间内，**也不允许重入**。原因：条件2检查的只是"最终触发止损那一刻的价格"，不检查"这笔交易历史上是否已经走到过TP1"——完全可能出现"价格冲高到TP1成交后又回落、最终止损价恰好落在允许区间"这种情况，这种情况说明趋势已经得到过真实确认后又反转，不属于"刚起步就被噪音扫出"的场景，不该重入。
6. **【本版新增】当前持仓档位必须是强趋势（tier=2）。** 弱趋势（tier=0）和中趋势（tier=1）档位下的雷达扫出，一律不触发重入。重入机会只留给最有把握的强趋势场景，弱/中趋势的回调更可能是真实趋势减弱而非纯粹的噪音扫损，不值得用重入去博一次翻本。当前档位判断复用开仓时已经确定并全程冻结的`tier`标记（该标记已用于雷达跟踪步长、呼吸空间等参数选择，无需新增数据来源）。

### 8.2 重入窗口期

ETH窗口期2根K线（约3小时），XAU窗口期3根K线（约2.25小时）。超过窗口期放弃本轮重入。

### 8.3 重入价格计算（本节为精确定义，替代此前的模糊表述）

```
多单重入价 = min(最近一根已收盘的5分钟K线的最低价 + 1个tick, TV信号价 × 0.997)
空单重入价 = max(最近一根已收盘的5分钟K线的最高价 - 1个tick, TV信号价 × 1.003)
```

**精确定义澄清**："最近一根已收盘的5分钟K线"指的是**在计算这一刻，时间上最近的、已经完整走完的一根5分钟K线**，不是过去若干根K线里的最低/最高值，也不是当前正在形成中的未收盘K线。每次挂单超时被撤销、需要重新计算价格时，都要重新拉取"当时那一刻"最新的一根已收盘5分钟K线，不能沿用上一次计算时的旧数据。

如果5分钟K线数据不可用，使用3分钟K线作为备选，定义方式相同（最近一根已收盘的3分钟K线）。

**重入价格必须优于上一次开仓价，否则不触发重入**（多单要求重入价更低，空单要求重入价更高）。

### 8.4 重入后的雷达系数与启动阈值

重入成功后，跟踪步长和每次跟进幅度使用**比首次开仓宽松一档**的参数（比如首次判定中趋势，重入后按强趋势档位的跟踪参数执行）。雷达启动阈值固定使用"到达TP2价格"（见5.1）。档位递进只在重入成功时发生，不影响TP1、TP2、TP3限价单的价格和数量。

### 8.5 不允许重入的情况

硬止损平仓绝对不重入；亏损平仓不重入；TV已发出平仓或反向信号时不重入；超过窗口期不重入；已经重入过一次不重入；重入价格无法优于上一次开仓价不重入；**TP1限价单已经成交过不重入（本版新增）**；**当前档位不是强趋势（弱趋势或中趋势）不重入（本版新增）**。

## 第九部分：重复挂单根本性防护与平仓完整性保障

### 9.1 本地订单状态表

每个挂单生成唯一订单标签（品种、方向、价格、开仓时间、随机数组合生成SHA-256哈希）。挂单前必须检查本地状态表，如果存在该品种任何未完成状态的订单标签，绝对不允许再次挂单。**无论交易所查询返回什么结果，只要本地状态表中有未完成的订单标签，就不执行新的挂单操作。**

### 9.2 明确点名历史bug模式，作为反面案例

**此前出现过的具体故障模式**：查询持仓接口失败或超时，代码没有正确处理这个失败，而是默认"查询不到=没有挂单"，于是继续执行挂单逻辑，导致同一个价位被反复挂出几十笔一模一样的限价单，堆积在盘口上。**这个模式必须被彻底杜绝**，具体规则：

- 任何查询操作（持仓查询、挂单查询）返回失败、超时、或者返回内容不完整/格式异常，**一律视为"状态未知"，不允许当作"无持仓"或"无挂单"处理**。
- 状态未知时，唯一允许的动作是：重试查询（按第十一部分的退避策略），或者达到重试上限后触发告警、暂停该品种操作，**绝对不允许在状态未知的情况下执行任何新的挂单**。
- 本地状态表的"未完成订单标签"，是判断"要不要挂单"的唯一依据，交易所查询结果只用于核对，不能在核对失败时反过来放弃本地状态表的记录。

### 9.3 挂单数量硬上限

任何时候该品种未成交挂单总数不得超过5笔。超过立即触发严重告警，暂停该品种所有交易，人工介入。

### 9.4 平仓完整性验证（本版新增，杜绝幽灵单、蚂蚁单、反向单）

**核心原则：任何一次平仓动作（无论是TP成交、止损触发、还是反转信号触发的平仓），执行完毕后必须立即验证盘口已经清理干净，不能只是"发出了撤单请求"就算完事。**

**数量精度处理（蚂蚁单的另一个根源，本版新增）**：TP1/TP2按10%/20%拆分总仓位、以及部分成交产生的剩余数量计算，都可能出现不满足交易所最小下单量（lot size）或最小名义价值（min notional）要求的"零头"。处理规则：拆分TP1/TP2数量时，按交易所要求的精度向下取整，**多出来的零头全部并入TP3对应的剩余仓位**（TP3本身没有限价单，这部分零头会自然并入雷达管理的70%仓位里，不单独产生无法成交的碎单）。如果TP1/TP2部分成交后剩余的零头本身就小于交易所最小下单量，无法再挂出对应的限价单，**直接对这部分零头执行市价平仓，不要让它以挂单形式长期滞留**（这类无法正常挂单的零头，本身就是蚂蚁单的主要来源）。

具体流程：

1. 平仓（市价全平或止损触发）执行完成后，**立即撤销该品种所有还在挂着的关联订单**——包括没成交的TP1/TP2/TP3剩余部分、硬止损单、雷达止损单，一个都不能漏。
2. 撤单请求发出后，**必须再查询一次该品种的未成交挂单列表，确认列表为空**。如果查询结果不为空（说明有撤单请求失败、或者存在此前未被追踪到的残留订单，也就是"幽灵单"），**立即对列表里的每一笔剩余订单单独发起撤销**，直到确认清空。
3. 如果连续3次查询仍然发现残留订单撤不干净，触发严重告警，人工介入，**该品种暂停接受新的开仓信号，直到人工确认盘口已清空**。
4. 特别注意"蚂蚁单"（因为多次部分成交、拆单、精度舍入产生的极小额残留订单，可能小到查询列表时容易被忽略）——验证盘口清空时，**任何数量大于零的挂单都算作残留，不能因为数量很小就跳过**。

### 9.5 防止"多余份量的限价单变成反向单"（本版新增）

这是9.4的一个具体高危场景，单独强调：如果平仓时下单数量的计算出现错误（比如没有按第六部分6.4的要求，用交易所实时查询的真实持仓做上限，而是用了一个偏大的本地记录数值），**平仓下单的数量可能超过实际持仓量**——超出的部分不会"平不出去"，而是会**直接开出一笔反方向的新仓位**（比如本来是要卖出平多，结果卖出数量超过持仓量，超出部分变成了裸空仓）。

**强制规则**：

- 任何平仓下单，数量必须严格等于（不能大于）第六部分6.4中查询到的交易所真实持仓数量。
- 下单前的最后一步，代码里必须有一个显式的数值比较：`平仓下单数量 <= 交易所真实持仓数量`，如果这个比较不成立，**直接拒绝执行这次下单，触发告警，不允许"四舍五入"或"就近取整"之类的模糊处理**。
- 平仓成交后，按9.4流程核对持仓是否真的归零；如果核对发现持仓方向发生了翻转（比如本该平多之后是零持仓，结果查出来变成了空头持仓），说明发生了超卖变反向单的严重故障，**立即触发最高级别告警，暂停该品种所有自动化操作，需要人工介入手动处理这笔异常仓位**。

### 9.6 平仓操作的幂等性

平仓这个动作本身也需要幂等保护：如果因为竞态条件（比如TP成交事件和反转信号几乎同时到达），同一笔仓位的平仓请求被触发了两次，**第二次平仓请求必须先查询当前持仓，如果已经是零持仓，直接判定为"已完成"、跳过本次操作，不能对着已经是零的持仓再发一次卖出/买入指令**（这同样会导致开出反向仓位）。

### 9.7 操作原子性

所有涉及挂单状态变更的操作严格按照"先查状态、再执行、再更新状态、再核对"的流程执行。

## 第十一部分：钉钉通知

### 11.1 通知内容清单

- **开仓通知**：品种、方向、价格、数量、当前档位、硬止损价、TP1/TP2/TP3价格。
- **雷达激活通知**：激活价格、当前档位、初始止损上移位置、本次是首次开仓还是重入开仓。
- **止损移动通知**：新止损价、当前浮盈、当前档位。
- **TP成交通知**：成交档位（TP1或TP2，TP3无限价单，不产生此类通知，TP3部分的退出统一走"雷达激活/止损移动/平仓"这几类通知）、成交价格、剩余仓位比例。
- **平仓通知**：平仓来源（TP1/TP2/TP3/雷达止损/硬止损/反转保护）、平仓价格、盈亏、档位。
- **重入尝试通知**：尝试原因、重入价格、当前档位。
- **重入成交通知**：成交价格、档位、窗口期剩余时间。
- **重入放弃通知**：放弃原因（窗口期过期/价格不优/方向失效）。
- **重启恢复通知**：重启后状态核对结果，包含是否发现不一致、修正内容。
- **异常处理通知**：见第十二部分，交易所异常发生时的告警。

每条消息以品种标签开头（ETH或XAU），然后是事件类型，接着详细参数，最后是档位信息。

## 第十二部分：交易所异常处理（新增章节）

### 12.1 下单被拒绝（保证金不足等）

- 记录详细错误日志，包含拒绝原因、尝试的订单参数。
- **不自动重试下单**（避免在保证金不足的情况下反复尝试导致更多无效请求）。
- 立即触发告警通知，暂停该品种新开仓（已有持仓的止损/止盈单不受影响，正常维护）。
- 需要人工确认账户资金状况后手动恢复该品种交易。

### 12.2 交易所API临时不可用（网络超时、5xx错误等）

- 采用指数退避重试：首次立即重试，之后每次重试间隔翻倍（比如1秒、2秒、4秒、8秒），最多重试5次。
- 重试期间，价格监控（WebSocket）如果仍然连通，继续正常记录价格，但不执行任何下单/改单/撤单操作。
- 5次重试均失败后，触发严重告警，暂停该品种所有自动化操作，进入"仅监控不操作"模式，等待人工介入或API恢复后自动检测恢复。
- API恢复检测：每隔30秒尝试一次简单的只读请求（比如查询账户信息），成功后自动退出"仅监控"模式，并立即执行一次持仓核对（参照第七部分7.3流程）。

### 12.3 订单被交易所单方面取消

这种情况通常发生在交易所风控介入、极端行情下的强制减仓、或者交易对本身状态变化（比如合约下架维护）。

- 检测方式：依赖WebSocket订单状态推送，收到"已取消"但本地状态表未曾主动发起撤销请求，即判定为交易所单方面取消。
- 处理流程：立即触发严重告警日志（区别于正常撤单，标注为"异常取消"）。立即执行一次强制持仓核对（同7.3流程），确认当前真实持仓和挂单状态。根据核对结果，重新挂出必要的保护性订单（尤其是如果被取消的是止损单，必须优先重新挂出）。
- 如果同一品种在短时间内（比如10分钟内）连续发生3次以上异常取消，判定为交易所层面可能存在系统性问题，暂停该品种所有操作，人工介入。

### 12.4 通用原则

任何交易所异常情况下，**优先保证已有仓位的止损保护不丢失**，其次才考虑是否继续新开仓或重入。宁可暂停交易，也不能让仓位在没有止损保护的情况下暴露风险。

## 第十六部分：给Cursor的最终指令

### 16.1 核心原则

本地状态表是唯一真相源。任何查询失败都不允许默认"没挂单"然后重新挂单，必须等待下一次查询周期或触发告警。每个品种同时存在的未成交挂单总数不得超过5笔。每笔挂单必须有唯一订单标签，标签在本地状态表中追踪全程。任何操作都遵循"先查状态、再执行、再更新状态、再核对"的流程。**所有影响仓位安全的状态必须持久化，VPS重启不能让在途仓位失去保护。**宁可错过，不要做错。

### 16.2 实施顺序

1. 先清理旧逻辑，确保无残留后再实现新功能。
2. 实现硬止损动态计算和统一呼吸垫系数（1.15）。
3. 实现雷达延迟启动（按TP1/TP2绝对价格锚定，不再用距离×系数），首次开仓激活价格=(TP1+TP2)/2，重入开仓激活价格=TP2。
4. **实现状态持久化和重启恢复流程（第七部分）——这一步优先级很高，建议在实现重入机制之前先完成，因为后续所有功能都依赖状态能够被可靠地保存和恢复。**
5. 实现重入机制，最多一次，明确"最近已收盘5分钟K线"的取值逻辑。
6. 确认TP3全程不挂限价单，完全交给雷达管理，删除任何"TP3限价单与雷达互斥"的旧代码。
7. 实现交易所异常处理（第十二部分）。
8. 更新钉钉通知。
9. 完成测试验证（本地→模拟盘20U，含重启测试和异常场景测试→实盘小仓位）。
10. 三端同步部署。

### 16.3 最终交付要求

代码必须通过所有测试场景验证，尤其是重启恢复和交易所异常处理这两块新增内容。日志完整可追溯。钉钉通知区分品种和事件类型。文档同步更新，包括README、部署文档、配置说明。三端commit hash一致。

## 第十七部分：一句话总结

单一币安账户，状态按品种（ETH/XAU）独立维护。硬止损是底线，呼吸垫统一1.15不分档。雷达是骑士，但使命大幅收窄——TP1(10%)和TP2前半段完全交给硬止损与TP1/TP2限价单自己守护，雷达首次开仓要等价格走到TP1-TP2区间中点才接管，重入开仓要等价格真正到达TP2才接管，用TP1/TP2绝对价格直接锚定。TP3(70%)永远不挂限价单，没有价格天花板，完全交给雷达追到趋势尽头，雷达跟踪计算统一使用TV传来的atr字段，VPS不再尝试独立拉取真实ATR（币安没有和策略周期匹配的原生K线，这条路走不通）。重入最多一次，窗口期限制，价格必须优于上次开仓价，重入价格取"最近一根已收盘K线"而不是历史窗口，且只有TP1从未成交过、当前档位是强趋势时才允许重入。VPS任何时候意外重启，所有状态从持久化存储恢复，止损保护必须在恢复流程的最高优先级完成。交易所异常（拒单、超时、单方面撤单）有明确的暂停与重试策略，优先保证已有仓位止损不丢失。重复挂单被本地状态表坚决阻止。旧代码全部清理无残留。等待真实TV信号到达，系统将自动执行完整流程。
